## 一、产品背景与定位

### 1.1 一句话定位

**用户问"智能手环怎么连手机"，系统从产品说明书里检索相关段落，让大模型生成一段有依据、不瞎编的回答。**

### 1.2 需求背景与痛点分层

一个好产品往往同时服务多个角色。本产品的价值对三类角色各不相同：

| 角色 | 痛点 | 本产品如何解决 |
|------|------|---------------|
| **C 端用户** | 说明书又长又难找，人工客服要排队、有下班时间 | 7×24 即时问答，直接定位到说明书相关内容 |
| **企业客服团队** | 重复问题占用大量人力，培训成本高 | AI 拦截标准化问题，人力聚焦复杂问题 |
| **企业管理者** | 客服质量不可控、不可量化 | 内置准确率评测，质量可监控、可优化 |

### 1.3 为什么选 RAG 而不是直接问大模型 / 微调

直接调大模型有三个致命问题：**幻觉**（一本正经编造"续航 30 天"）、**知识不私有**（不知道你家这款手环的具体参数）、**无法溯源**（答不出依据）。

| 方案 | 问题 |
|------|------|
| 直接调大模型 | 幻觉、不私有、不可溯源 |
| 微调（Fine-tuning） | 贵、慢、知识更新要重训、易过拟合 |
| **RAG（本方案）** | 知识放外部文档，随时增删改，模型不动；可溯源 |

> **选 RAG 的产品理由**：说明书会频繁更新（出新品、改参数），RAG 改个 txt 文件就行，微调每次都要重训。对需要持续维护的客服场景，RAG 是更务实的选择。

### 1.4 三大功能模块

```
┌─────────────────────────────────────────────────┐
│  SmartGuide AI                                    │
├─────────────────┬──────────────┬─────────────────┤
│  问答系统        │  实时评测     │  一键评测        │
│  (核心体验)      │  (质量监控)   │  (回归测试)      │
│  给 C 端用户     │  给运营/PM    │  给开发/PM       │
└─────────────────┴──────────────┴─────────────────┘
```

> 拆成"实时"和"一键"两个评测页，对应两种场景：实时评测看**线上真实流量**表现（监控思维），一键评测跑**固定 100 题标准集**验证 Prompt 改动后是否变差（回归测试思维）。分开才能"可复现、可对比"。

## 二、目标用户与使用场景

### 2.1 用户画像

**C 端用户**：刚买了智能手环/门锁，说明书翻了几页看不懂，想快速问"怎么配对""防水几级"。

**B 端（产品使用者/付费方）**：智能硬件品牌的客服负责人，要降本增效、量化客服质量。

### 2.2 使用场景

- 用户开箱后遇到连接/配对问题，不愿翻说明书
- 用户想查具体规格参数（续航、防水等级、色温范围）
- 故障排查（无法充电、连接断开、闪烁）
- 企业定期回归测试 Prompt 改动、监控线上质量

## 四、产品决策权衡（面试可讲）

> 本 PRD 的核心。这几个决策体现了"产品思维"而非"技术炫技"。

### 决策 1：为什么默认不用向量检索？（v0.1 决策 + v1.x 修订）

**v0.1 的判断**：
- 主流 RAG 用**向量检索**（语义强，但要装 PyTorch、向量库，部署重、Windows 有 DLL 坑）。
- 本项目**刻意选轻量关键词匹配**：知识库小（5 份文档），中文客服问题**关键词重合度高**（用户问"续航"、文档也写"续航"），语义检索优势发挥不出来。
- **产品理由**：目标场景要求"普通 Windows 电脑 2 分钟装完就能跑"。这是"够用就好"（good enough）。

**v1.x 的修订（实现后回头修正）**：
- 单纯 bigram + Jaccard 有两个实测问题：① 分母用并集，**短段落反而占优**（"产品概述"这类两三行的块稳拿第一）；② 换个说法就完全匹配不上（"充不进电" vs 手册"无法充电"）。
- 因此改成三层结构：
  1. **默认 BM25**（`k1=1.5, b=0.75`，标题词加权 3 倍），纯 Python、零依赖，仍是"2 分钟能跑"；
  2. **同义词扩展**补口语表达（"充不进电" → 无法充电/触点/充电器），这是对 bigram 缺陷的直接补丁；
  3. **向量检索与混合检索（RRF）已实现但默认关闭**，`RETRIEVER=hybrid` 才启用。
- **为什么不默认开向量**：目标客户是内网/离线环境，首次运行要下 ~100MB 模型，装不上就整个检索不可用；而规格数字类问题（"5ATM""100 枚指纹"）恰恰**需要字面精确匹配**，向量反而容易糊。
- **结论**：不是"放弃向量"，而是"把向量做成可选增强，默认给一条在任何环境都能跑通的路，并留出降级开关"。

### 决策 2：为什么要在调 AI 之前先拦截"无效问题"？

三个理由全是产品考量：
1. **省钱**：每次调用大模型都花钱，"你好"不值得问 AI。
2. **省时**：本地判断 <1ms，调 AI 要几秒，无效问题秒回更友好。
3. **数据干净**："你好"若计入准确率会污染统计。

> 本质是**用便宜手段处理简单情况，把贵的资源留给真正需要的**——成本意识是 PM 基本功。

### 决策 3：为什么"超纲问题"要单独一类，而不是算错？（最精妙的产品判断）

用户问"手环多少钱"，知识库里没有价格。AI 老实说"该信息不在使用指南中"——**这其实是正确行为**！因为产品就是要它别瞎编价格。

如果把这种"正确的拒答"算成"答错"，会得出荒谬结论：**AI 越诚实，准确率越低**，逼着团队把 AI 调成什么都敢答。

> 背后的价值观：对客服 AI，**"知之为知之，不知为不知"比"无所不答"更重要**。乱答的代价远大于不答。

### 决策 4：为什么两个指标都要（有据可查率 + 正确率）？

早期只做了「方案A（查依据）」，后来补上了「方案B（对标准答案）」，现在是双指标：

- **有据可查率（groundedness，原方案A）**：回答关键词有多少能在引用文档里找到支撑。度量"每句话有没有出处"。
- **正确率（correctness，原方案B）**：回答覆盖人工标准答案关键点的比例。度量"答得对不对"。

**为什么不能只留一个（这是这条决策的核心）**：

| | 有据可查率高 | 有据可查率低 |
|---|---|---|
| **正确率高** | 正常 | **蒙对了**——不可信，下次就错 |
| **正确率低** | **照着资料答错了**——资料本身有问题 | 检索没找到 |

- 只看有据可查率 → 会奖励"复读文档原词"，哪怕答非所问；
- 只看正确率 → 会奖励"碰巧说中"，掩盖幻觉风险。

> **指标的定义权决定团队优化方向**。客服产品最怕幻觉，所以有据可查率是主指标；但主指标必须配一个"答得对不对"的对照，否则会优化出"很老实但没用"的系统。

### 决策 5：为什么把「分类、准确率、引用文档」展示给用户？

AI 回答天然让人怀疑"是不是瞎编的"。把引用文档亮出来，用户能自己核对，信任感大幅提升。**可解释性 → 信任**，这是 RAG 相比纯大模型的产品优势，在 To B 场景往往是能不能签单的关键。

## 五、指标体系

### 5.1 北极星指标

**问题自助解决率** = 用户问完没再转人工、没再反复追问的比例。

> 选它而非"提问量/准确率"的理由：产品核心价值是"替代人工客服"，自助解决率最能代表价值兑现。提问量多可能反而意味着"一次答不好，用户反复问"。准确率是**支撑指标**，服务于自助解决率。

### 5.2 支撑指标

| 指标 | 定义 | 说明 |
|------|------|------|
| 有据可查率（groundedness） | 回答关键词被文档支撑的比例 | 防幻觉能力。当前实测 60.5%，字面匹配口径偏严 |
| 正确率（correctness） | 答案覆盖标准答案关键点的比例 | 当前实测 70.3%，答对率 73.3% |
| 拒答准确率 | 超纲问题正确拒答的比例 | 该拒答时拒答，不瞎编 |
| 无效拦截率 | 无效问题被本地拦截的比例 | 成本控制 |
| 响应时间 | 从提问到出答案 | P95 < 5 秒 |
| 平均准确率（分题型） | 连接/功能/规格/故障 分类统计 | 定位系统弱点 |

## 六、技术方案（与代码对齐）

### 6.1 完整数据流

```
用户提问 "智能手环防水等级?"
   │
   ▼
① 有效性检查（本地规则，<1ms）  ──无效──> 直接拦截，不调 AI
   │ 有效
   ▼
② RAG 检索（设备定向 + 同义词扩展 → BM25 打分，top_k=5 段最相关段落）
   │  （可切换 bigram / hybrid；无召回则直接判超纲）
   │
   ▼
③ LLM 生成（拼 Prompt → 调 OpenAI 兼容 API → 429 重试）
   │
   ▼
④ 三级分类（无效 / 超纲 / 有效）
   │
   ▼
⑤ 有据可查率（有效问题才计算）+ 正确率（有标准答案时计算）
   │
   ▼
⑥ 埋点（SQLite：会话/耗时/检索器/分类/指标/是否追问）

渲染：答案 + 分类 + 指标 + 引用文档 + 👍/👎 反馈
```

### 6.2 检索方案（默认 BM25，向量与混合可选）

**知识库规模**：5 份手册、约 1.1 万字、切成 **159 个知识块**（按空行切，保留"标题+步骤"完整）。

**默认：BM25**（`src/retrieval.py` 的 `BM25RAG`）
- 中文切相邻二字组，英文数字整段保留（保型号精度）；
- 打分 `idf × 词频饱和项`，`k1=1.5`（防堆词）、`b=0.75`（长段落打折）；
- **标题词加权 3 倍**：手册里标题就是这一节的命题；
- 结果归一化，第一名恒为 1.0。

**前置两步加工**：
1. **设备定向**：命中"手环/手表/门锁"等词时只在该设备手册内检索，并把设备词从查询里删掉（否则泛泛的"产品概述"会霸榜）；
2. **同义词扩展**：口语 → 手册术语（"充不进电" → 无法充电/充电故障/充电触点）。

**可选：混合检索**（`RETRIEVER=hybrid`）
- BM25 与向量（`BAAI/bge-small-zh-v1.5`）各召回 20 条，用 **RRF**（`1/(60+名次)`）融合后取 5；
- RRF 只看名次不看分数，因为两路分数量纲不同、不能直接相加；
- 可再叠 `bge-reranker-base` 交叉编码器重排（`RERANK=true`）；
- 向量依赖装不上时自动降级为 BM25，不阻塞主流程。

**为什么这么选**：BM25 强在型号数字精确匹配，向量强在换说法，二者互补而非替代；
默认走 BM25 是为了任何内网环境都能跑起来。

### 6.3 三级问题分类

| 级 | 类型 | 判断 | 处理 |
|----|------|------|------|
| 1 | 无效 | 过短 / 无设备词 / 无动作词 | 本地拦截，不调 AI |
| 2 | 超纲 | AI 回答含拒答信号词 | 不计入准确率 |
| 3 | 有效 | 正常回答 | 计入准确率统计 |

### 6.4 有据可查率（groundedness）算法

1. 提取 AI 回答的关键词（改进版：先抓"数字+单位"，再去虚词，再抓 2-5 字短语）；
2. 提取检索文档的关键词；
3. `准确率 = 有支撑的关键词数 / 回答总关键词数`；
4. 返回分数 + 详情（哪些词有/无支撑），供前端展示。

### 6.5 可插拔大模型与容错

- OpenAI SDK 统一接口，`.env` 换 `LLM_BASE_URL` 即切换 MiniMax / 通义 / DeepSeek / 本地 Ollama；
- 429 限流自动重试（3 秒 → 6 秒 → 9 秒，最多 3 次），故障不中断评测。

## 八、范围外 / 风险 / 里程碑

### 8.1 范围外（本期仍不做）
- ❌ 完整用户账号体系（目前只有管理员单密码门）
- ❌ 多租户与角色权限
- ❌ 图文混合检索、语音交互

**已从"范围外"移入已实现（v1.x）**：
- ✅ 用户反馈按钮（👍/👎）
- ✅ 多轮对话上下文（最近 3 轮可配）
- ✅ SQLite 埋点与自助解决率看板
- ✅ 向量检索与混合检索（可选启用）
- ✅ 可复现的 100 题评测与结果落盘

### 8.2 风险与缓解

| 风险 | 缓解 |
|------|------|
| 关键词检索不懂语义（"防水吗" vs 文档"5ATM"匹配不上） | 已加同义词表；进一步可开 `RETRIEVER=hybrid` 走混合检索 |
| 拒答信号词误判（正常回答含"无法"） | 与 Prompt 话术强耦合，需同步维护 |
| 有据可查率可能被"复读文档原词"刷高分 | 已增加正确率做对照；进一步可引入 NLI 模型做支撑判断 |

### 8.3 里程碑
- **✅ MVP（v0.1）**：RAG 问答 + 三级分类 + 有据可查率 + 实时/一键评测。
- **✅ v1.1（已完成）**：用户反馈按钮、SQLite 埋点与自助解决率看板、多轮对话、管理员知识库维护。
- **✅ v1.2（已完成）**：可切换检索后端（BM25 / bigram / hybrid + RRF + rerank）、
  双指标（有据可查率 + 正确率）、100 题金标准评测集与可复现落盘、18 个单元测试。
- **⬜ v2.0（远期）**：多租户与角色权限、图文混合检索、评测集扩到 300+ 题并做人工校准。
